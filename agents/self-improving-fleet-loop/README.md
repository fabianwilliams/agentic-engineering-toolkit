# Self-Improving Fleet Loop

> A Reliability Kit discipline. The 5-stage agentic loop applied to a small autonomous-agent fleet running on consumer-tier always-on hardware. Sensor → policy → tool → quality gate → learning, with a constitutional gate at the start and a receipt-emitting gate at the end of every iteration.

---

> **By the end of this doc you will know what the YC self-improving company framework means when you do not have YC's budget, a research staff, or a fleet of frontier-model orchestrators. You will know which of the five stages your existing agent fleet already covers, which is the binding constraint, and which discipline pays it down.**

---

## The discipline

A self-improving agent fleet runs the same 5-stage loop continuously:

| Stage | What it does | What goes wrong without it |
|---|---|---|
| **Sensor** | Records real-world input: emails, tickets, telegram digests, telemetry, receipts, ad-hoc operator chat | Failures vanish into operator memory; the next session has no learning fuel |
| **Policy** | Names what the agent may do, what needs approval, what must be logged | Agents fabricate actions; no audit trail; no closed loop |
| **Tool** | Deterministic APIs the agent calls (Brevo, Hunter, Stripe, Graph, MCP servers) | Tool-call results are not legible; integrations break silently |
| **Quality gate** | Receipt-style audit trail per iteration; eval-style scoring; operator-approval surface for high-risk actions | Bad outputs ship; failures look like successes |
| **Learning** | Watches failures, drafts the fix, opens a PR or memory update, routes to operator for one-click approval | The loop never closes; same incident recurs; the box does not get better |

Two gates wrap the loop:

- **Constitutional gate** at iteration start: the rules the loop must honor (per-box constitution file). Inspired by Ralph v2 but tuned for runtime rather than project work.
- **Receipt gate** at iteration end: every iteration produces a verifiable artifact. Same primitive as the audit-trail receipt in the partner-facing storefront ([[Announce Intent Before Action]]), now applied to the loop itself.

If you cannot answer "what fired" for a given iteration with a URL or file path, the loop is not honest.

## Why this matters now

Y Combinator published a 2026-05-21 talk on self-improving companies (drawing on Jack Dorsey's tweet thread and Diana Hu's earlier framing). The core claim: a company is no longer a Roman-legion hierarchy with humans as the information conduit; it is a set of recursive AI loops with humans at the edge making contact with reality. The companies that win the next decade are the ones whose loops close overnight.

This discipline takes that framing and applies it to a different scale. **You do not need YC's frontier-model orchestrator budget to run the loop.** A small autonomous-agent fleet on consumer-tier hardware (three boxes, one Mac mini class machine per box, a couple of LLM API keys, Telegram for the operator surface) can run the same loop with the same closure semantics. The differences are quantitative (token budget, iteration frequency, action blast radius), not architectural.

## Where most fleets get stuck

Most small autonomous-agent fleets get stages 1-4 right and then stall on stage 5. The signs:

- Telegram channel full of daily summaries, none of them consumed by an agent
- RCA files written by hand after an incident, never read by the next session
- Memory rules updated by the operator, never proposed by the fleet itself
- "We will get to that bug in the backlog" without a closed-loop owner
- Same incident class recurs every two or three weeks

The loop is open at stage 5. The fleet observes; it does not learn. The discipline below names what closes that gap.

## The five stages, applied to a small fleet

### Stage 1: Sensor

What good looks like for a small fleet:

- All operator-agent traffic recorded (Telegram, iMessage, Slack, email)
- All cron-action outputs emit a verifiable artifact (summary + log file + receipt)
- All third-party events captured (Brevo opens/bounces, Hunter quota, App Insights traces)
- Daily summary generated by a deterministic script, not an ad-hoc operator typing

Anti-pattern: "we have logs in CloudWatch / Application Insights / Datadog." Logs are sensor *fuel*; they are not the sensor layer. A sensor produces structured input the next stage can act on. Without the structure, the loop cannot close.

### Stage 2: Policy

The per-box constitution file. Codifies:

- Which actions the fleet may run autonomously
- Which actions require operator approval (Telegram thumbs-up or equivalent)
- Which actions must be logged regardless of outcome
- Which categories of failure escalate to a human immediately
- Token-budget ceilings and the kill-switch threshold

The constitution is **machine-readable**, not a prose document. Prose is documentation; the loop needs declarative rules.

### Stage 3: Tool

The deterministic APIs the loop calls. For a small fleet, this is usually: CRM (Brevo), enrichment (Hunter), payments (Stripe), comms (Graph or Telegram), agent surfaces (MCP servers).

The discipline at this stage is **wrapper-script enforcement**: no LLM freelance calls to APIs. Every API call goes through a wrapper that emits `summary_lines + verified` so the receipt at stage 4 can verify the action fired against disk state, not claim it fired based on the LLM's first-person narration.

### Stage 4: Quality gate

Per-iteration audit-trail receipt. Same shape as the [[Announce Intent Before Action]] discipline's receipt: every check that fired, in order, with timestamps and pass/fail/skip/warn status, in a verifiable artifact.

For a runtime loop, the receipt lives on disk (per-iteration directory, JSON file). The operator can fetch it; another agent can consume it; the next iteration's sensor can pick it up as input.

### Stage 5: Learning

The stage most fleets get wrong. What good looks like:

- Watch the latest iteration's receipt + last 24h of sensor data
- Classify each incident into one of four buckets: `update_memory`, `open_pr`, `escalate`, `noop`
- For `update_memory`: draft a `feedback_*.md` rule and post to operator with one-click approve / reject
- For `open_pr`: write the code change, push to a feature branch, open a draft PR with the receipt as evidence
- For `escalate`: structured Telegram message to the operator with the choice already framed
- For `noop`: explicit decision, logged, not silent

Single most-important constraint: **the operator approval is one click**. If the operator has to read 200 lines of context to decide, the loop has failed to do its job. The proposal must be self-explanatory in under 15 seconds of review.

## How this discipline differs from project-shaped frameworks

Frameworks like Ralph v2 (the constitutional-development pattern this kit's author uses for `projects/` work) are designed for **interactive code sessions** where a human reviews scope clarifications before execution begins. That Phase 1 *stop and wait* gate is correct for project work; it is wrong for an always-on runtime loop.

The self-improving fleet loop has no Phase 1 clarifications stage. It has:

- A constitutional init (once per box, on deployment)
- A continuous 5-stage iteration (forever, until token budget hit or operator kill)
- A goal-backward verification per iteration (the receipt)
- A daily observability report (the rolled-up receipts)

The reference runtime engine for this discipline is **[[ADOTOB Loop]]** (`agents/adotob-loop/`): a constitutional bash loop that implements the five stages with per-box constitution, sensor scripts, policy gate, quality gate, and operator-approval surface. Apache-2.0 licensed.

## The legibility prerequisite

YC's first prescription for self-improving companies is "make everything legible to AI" (see `knowledge/wiki/concepts/make-everything-legible-to-ai.md`). The fleet-loop discipline depends on this: if conversations vanish into operator memory, the sensor stage is starved and the learning stage has nothing to act on.

For a small fleet, the minimum legibility surface is:

- Every Telegram thread the operator has with the fleet (already captured if you use a bot)
- Every email the fleet sends or receives (via Brevo / Graph / IMAP archive)
- Every API call the fleet makes (via wrapper-emitted log lines)
- Every operator decision recorded as a memory rule, RCA file, or commit message
- Every receipt the fleet emits

If a class of decisions still lives in the operator's head, the discipline says: write it down in a memory rule, attach it to the next operator-approval prompt, let the learning agent see it.

## What this discipline pays down

In supervision-debt language ([[Paying Down Supervision Debt|see the launch post]]): the fleet-loop discipline pays down the learning row of the 5-control-point map. The other four rows (runtime, identity, data, tool) get their own gates in the partner-facing kit. Learning is the runtime-only row, because closing the loop overnight is the property that makes a small fleet act like a bigger one.
